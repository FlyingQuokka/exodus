# WordPress Setup

Everything set up by hand on the WordPress side, in one place, so no step is hunted for across the Build-Plan. All of it is the human's work: no build agent can reach WordPress, FluentCart, FluentCRM, FluentAffiliate, FluentSupport or Stripe's dashboards. Most of it is done before phase 1 starts. The plugin step waits for the branch that builds `btv_checkout_guard`, which is after stream B merges. `Build-Plan.md` section 8e keeps the ordering and points here; the steps themselves live only here. Every step is repeated on the live account at phase 4 item 9.

Paths, hostnames and the local services are in `E:\Projects\AIBotShare\Docos\Build-Plan.md` section 8e, their one copy. No secret is written into this or any other document.

`{{domain}}` in these documents stands for the live domain, `botterverse.com`.

## 1. WordPress itself

**When:** before phase 1 starts.

- **The site.** The WordPress marketing site holds FluentCart, FluentCRM, FluentAffiliate and FluentSupport. It runs on the apex domain live and at `botterverse.debbie` locally. The application sits in the web root's `lab` folder and is reached only through its own subdomains, so WordPress's address can never serve it (`Data-Model.md` section 1b).
- **The pricing page.** The marketing site's pricing page shows each tier's monthly and annual price, with each buy link going through the application's route like the monthly ones (spec 6i). It is the entry to a subscription purchase. After testing, delete FluentCart's shop page so that no direct product address remains.
- **Help redirect.** The BetterDocs article on buying packs has the slug `booster-packs`. Redirect `/docs/credit-packs/` to `/docs/booster-packs/` where the site has the old address (8 November 2026).
- **Application Passwords.** Created in the WordPress user's own profile, one per purpose, so either can be revoked alone:
  - one for FluentCart's API, needed at phase 1, which the application uses to fetch an order from FluentCart (`GET /orders/{id}`) when a feed prompts it, for the coupon code and the ids
  - one for the FluentAffiliate and FluentCRM APIs, needed at phase 3, which the application uses to create an affiliate record, deactivate or reactivate one, read an affiliate's referrals for the Affiliates page, create and read a payout batch, mark a transaction paid and deliver CRM outbox rows

  Both go in the application's `.env`, never in a document.
- **The plugin from the repository.** `btv_checkout_guard` is an ordinary plugin, built by the stream that owns it and held under `wordpress/plugins/` in the build root. It is not a must-use plugin.
  - **Locally:** it is linked into the WordPress site's `wp-content/plugins` with a directory junction, made in PowerShell with `New-Item -ItemType Junction -Path <link> -Target <folder>`, then activated. Never use `ln -s`: Git Bash silently makes a copy instead of a link, so a later change to the plugin would not reach WordPress. A true symlink needs admin rights or Developer Mode; a junction needs neither.
  - **Live:** no links are used. Each deployment copies the folder into the live WordPress plugins folder after the pull (`Build-Plan.md` phase 0 item 16). Staff activate it once the first deployment has copied it.
  - `btv_checkout_guard` refuses the blocked billing countries through FluentCart's `fluent_cart/checkout/validate_data` hook, because FluentCart has no country setting of its own. It reads the list from the application's `sales.blocked_countries` setting, so staff edit it in one place and keeps it for 60 minutes. If the application cannot be reached it uses the last list it received and with no list at all checkout asks the buyer to try again later (spec 6i). It also refuses a second membership subscription for a customer who already holds one, unless the checkout is an upgrade. It refuses an upgrade from a plan set to end or a plan it cannot check (spec 6i). It never refuses a booster pack. The buyer is pointed to Subscription Plans in FluentCart's customer area. It also types a subscription order's FluentAffiliate referral `sale` where Lifetime Commissions typed it `lifetime_sale`, so its renewals still earn. The same answer carries `sales.founders_coupon_code`, which the plugin uses to carry the founders coupon onto a founder's next plan. It needs no setting beyond the two below.
  - **The current version.** Plugin version 2.0.19. It applies the founders coupon by itself when a signed-in founder's plan checkout opens and accepts it on a founder's cart after the offer closes, however it was closed (13 and 14 November 2026). A founder is a customer any of whose plans used it. The plugin asks the application whether a customer is a founder, so a coupon recorded with Set Coupon counts too. If the application cannot be reached the checkout uses FluentCart's coupons alone. A failed read of the list or of the founder question is tried again only after a minute. Each founder answer is kept for five minutes. Nothing is entered. Make the founders coupon a recurring percentage discount that includes every plan variation and only the plan variations, never a booster pack or a bump product. Close the offer with an end date or a status and never delete the coupon. Its five emails carry the Botters Lab logo, the sign-off and the footer, like the application's member emails (11 November 2026). The logo is built from the Application URL saved on its settings screen, so that address must be saved. Its purchase email lists the Botters Lab account first and the billing login second. On the first request after the update it replaces the saved purchase email body only where it is still the previous default (5 November 2026). A buyer can type a coupon code in any case: the plugin trims it and passes FluentCart the coupon's saved code, since FluentCart matches codes case-sensitively (5 November 2026, reported to FluentCart). Enter every FluentCart coupon code in lower case, for example `founder50`. The plugin saves a code entered with capitals again in lower case. A cart made before a code was re-saved may need the code applied again. When a member's account is anonymised it deletes their WordPress user and runs FluentSupport's eraser, keeping FluentCart's customer unlinked. It clears the payment email on their FluentAffiliate record, which otherwise stays for the commission history. A member who returns on the same email takes over the old user (5 November 2026). WordPress's Erase personal data screen is not needed for a closed member. It makes or finds a WordPress user for each member who verifies their email in Botters Lab, a subscriber with the lab username as its login. It signs them straight in to the support desk and the feedback page from the lab's Support and Feedback links whether or not they have bought anything. A later purchase on that email is linked to the same user at payment (4 November 2026). Members have no separate support account. On the first request after the update it changes "Botter's Lab" to "Botters Lab" in the saved subject and body of its five emails, keeping any other edits (4 November 2026). A member can type their Botters Lab username on the billing sign-in and lost password pages: the plugin asks the application which member holds it, using the Application URL and shared secret it already holds, so the WordPress server must be able to reach the application. A lab username never stands in for a staff login. All-In-One Security's instant lockout of invalid usernames must stay off. Otherwise a lab username the application could not resolve would lock the member out (4 November 2026). It also signs a member who is signed in to Botters Lab straight in to their billing account from the lab's Open the customer area and Change plan buttons. It signs them out of it when they sign out of the lab (4 November 2026). It does this for an ordinary buyer account only. Its two pages, `/billing-account/handoff/` and `/billing-account/sign-out/`, take form posts only and must not be cached or blocked by a cache, firewall or security plugin. The rewrite rules are saved again on the first request after the update. It also sends FluentCRM's sending chain through WordPress so the request carries a user agent, since All-In-One Security's rule "Ban POST requests with blank user-agent and referer" banned the site's own address when FluentCRM posted to itself with neither (3 November 2026). Keep that rule on. On a local site, where the Application URL's host resolves only to a private or loopback address, requests to it skip WordPress's certificate check, since WordPress trusts no locally made certificate. A live application's certificate is always checked. It rounds each new FluentAffiliate referral amount to the cent, since FluentAffiliate 1.7.0 saves it unrounded (their bug, confirmed 3 November 2026). It lets FluentCart Pro post its feeds to the saved Application URL's host when that host is a private address as on a local site. It allows no other host. The guard reads Stripe with FluentCart's own keys.
  - **Moving to 2.0.0.** Copy the new folder over the old one as at any deployment. Nothing is entered again. On the first request after it arrives the plugin moves each saved option from its old `abs_checkout_guard_` name to its `btv_checkout_guard_` name, changes the tags in the five emails' saved text to double braces and saves the rewrite rules again. A value already saved under a new name stays. The receipt page's shortcode is `[btv_create_account]`.
  - **After each FluentCart update.** After each FluentCart update, try one move up on a test account. If FluentCart has changed how it talks to Stripe the guard refuses every upgrade, showing "We could not check your plan just now".
  - **Its settings.** After activating it, open Settings > Botterverse Checkout Guard. Set **Application URL** (`btv_checkout_guard_app_url`) to the application's base URL with no trailing slash. Set **Shared secret** (`btv_checkout_guard_secret`) to the same value as `CHECKOUT_GUARD_SECRET` in the application's `.env`, a random value of at least 32 characters, since a shorter one switches the lab username lookup and the founder question off. The Application URL must be exactly the origin of the application's `APP_URL` (scheme, host and port), otherwise every press of the lab's billing buttons ends on the sign-in page. Set **Billing sign-in secret** (`btv_checkout_guard_handoff_secret`) to the same value as `BILLING_HANDOFF_SECRET` in the application's `.env`, at least 32 characters and never the value of another secret. The tick box **Clear the saved secret** switches the plugin's side off. Save, then load a FluentCart checkout to confirm it reads the list. On the same screen, check the subject and body of its five emails then save them: the buyer account, reset password, password changed, email changed and new email address emails. The plugin sends them in place of WordPress's own (`Spec-v1.md` section 6e).
  - **Where each secret goes.** FluentCart's own Stripe keys go in `wp-config.php`. Everything the application reads goes in its `.env` in the `config` folder beside the web root. Neither file is committed and neither is read back into a document. Section 6 below lists them all.

## 2. FluentCart

**When:** before phase 1 starts.

- Connect Stripe by API keys, never the "Connect with Stripe" button.
- Set the store currency to US dollars.
- Set renewals to gateway-managed, so each subscription is a native Stripe subscription that Stripe bills and retries.
- Set FluentCart's "prices entered with tax" setting to match `tax.price_behaviour`. FluentCart has its own tax engine and does not use Stripe Tax, so the two settings have to agree or a subscriber's price moves when tax is switched on (spec 6i).
- **Create one membership product** with a subscription variation for each tier and billing interval: twelve variations in all, six tiers each monthly and yearly. Name each for its tier and interval, for example “Novice Botter Monthly”. FluentCart allows Upgrade Paths only between variations of the same product, which is why the tiers share one product. A plan change runs through an Upgrade Path, which creates a new subscription and cancels the old one, so a missing path leaves that change with no route.
- **Every tier is an ordinary subscription with no trial**, Apprentice included. Apprentice is $5 monthly like every other tier is priced for its own interval. Each tier has one current `tier_price` row for each billing interval, monthly and annual (`Data-Model.md` section 3). FluentCart funds a plan change made through an Upgrade Path with a Stripe trial of the credit, so a subscription can show as trialing in Stripe after a change. That is expected and the application saves it as active.
- **Each tier’s annual price is in the tier table in** `Spec-v1.md` (Monthly Price and Annual Price) and is entered on the Feature matrix at launch like the monthly one.
- **Add the Upgrade Paths** inside that product, upward only, with Is Prorate set to Yes and no discount amount. A monthly plan moves to its own annual plan or a higher monthly plan, an annual plan moves to a higher annual plan and no path leads to or from Empire, which is not on sale. A member moves down by cancelling, then buying the lower plan once the plan ends, so no downward path is added (owner, 31 October 2026).
- **Create one Botter Booster Packs product** with the slug `booster-packs` and a variation for each pack (decided 20 October 2026, named on 10 November 2026): Starter, Builder, Launcher, Promoter and Campaigner. Buyers read "Botter Booster Pack". A site that has the product under an older name or the slug `credit-packs` renames it and redirects `/item/credit-packs/` to `/item/booster-packs/`. Each variation's id goes in the `credits.packs` setting with the pack's name, its price in cents and its credits.
- **Create five feeds to the application** in FluentCart's Integrations, one for each trigger the webhook register lists: Order Paid (`order_paid_done`), Subscription Activated (`subscription_activated`), Subscription Renewed (`subscription_renewed`), Order Refunded (Full) (`order_fully_refunded`) and Order Canceled (`order_status_changed_to_canceled`). Give each feed the same URL and two custom headers: `X-BTV-Feed-Secret` with the shared secret value and `X-BTV-Feed-Trigger` with that feed's trigger name as written in brackets here. FluentCart cannot sign a request, so the secret header is what the application checks. The body's trigger is not named, which is why each feed carries its own header. A partial refund has no feed: it reaches the application through Stripe's `charge.refunded`.
- **Record the ids.** Read the FluentCart variation id of each tier from FluentCart. The test variation id of each tier then goes in the phase 0 handoff and is entered on the Feature matrix (spec 8E.24) once stream C has merged. Until then stream B's tests use factories. FluentCart creates a new Stripe price for each purchase, so no Stripe price id is needed. The live variation ids are entered the same way at phase 4 item 9.
- **Record the yearly ids too.** Each yearly variation's test FluentCart variation id is entered on the Feature matrix with the interval `year` in phase 1, then the live one at phase 4 item 9, the same way as the monthly ones.
- Whoever renames a tier in the Back Office renames its FluentCart product too. The two are not synced, which is why the Feature matrix carries a standing warning.
- **The customer area page** is named `account`, so its address is `/account/`. If the page is ever renamed, save FluentCart's store settings then save Settings > Permalinks, because FluentCart keeps its own copy of the slug and builds its routes from it, then change `customer_area` and `upgrade_checkout` on Advanced settings (owner, 30 October 2026).
- **The receipt page** tells the buyer to create their Botters Lab account with the same email they bought with, so the purchase is added to it (`Spec-v1.md` section 6e). The page is the one chosen in **Select Receipt Page** (Settings > Store Settings > Pages Setup). Add a Shortcode block holding `[btv_create_account]` above its `[fluent_cart_receipt]` block. The plugin prints the sentence with a link built from its Application URL.

## 3. FluentCRM

**When:** before phase 1 starts.

- **Create the tags.** One per hook point in spec 6a: `Apprentice Botter`, `Novice Botter`, `Expert Botter`, `Pro Botter`, `Master Botter`, `Empire Botter`, `Downgraded`, `Cancelled`, `Dormant`, `Built First Bot`, `Published First Bot`, `First Sale`, `Migrated From GPT`, `Bot Market Seller`, `Bot Market Buyer` and `Auto Top Up` (renamed from `Power User` by the owner, 25 October 2026). Each tag then goes against its hook point on CRM Integration (spec 8E.21). A blank tag there means that hook does not fire, which is the only switch.
- **The application's hook register drives the tagging.** The `crm_hook` register in `Data-Model.md` section 12 names every hook point and the stream that fires it. Rows are written to the CRM outbox and delivered by a queued worker, so a CRM outage loses nothing. `tier_reached_apprentice` is one of those hook points, so Apprentice is tagged like every other tier. The register also carries the `remove_tag` action, which clears the previous tier tag on every tier change and on a lapse, so a member never holds two tier tags and a broadcast by tier never reaches the wrong people.
- **Ten more tags,** spelt exactly, before entering them on CRM Integration: `Upgraded From Apprentice`, `Upgraded From Novice`, `Upgraded From Expert`, `Upgraded From Pro`, `Downgraded From Master`, `Downgraded From Pro`, `Downgraded From Expert`, `Downgraded From Novice`, `Founder` and `First Commission`. After setting the Founder tag a superadmin presses Tag existing founders once. Each direction funnel removes its direction tag at its last step because otherwise it will not run a second time. `Downgraded` and the four `Downgraded From` tags now fire only in the rare case of a FluentCart Cancel followed by a cheaper re-buy before the Lapses step or when the new plan's event comes first.
- **Four plan ending tags,** spelt exactly, before entering them on CRM Integration: `Plan Ending Soon`, `Plan Ending Tomorrow`, `Plan Ends Today` and `Plan Ended`. They fire 7 days before, the day before, on the day and once ended, for a plan the member cancelled. Each has one short funnel sending at once, with no fixed waits. Stop any funnel when the member gains a tier tag. The wording and the funnel rules are in `docs/handoffs/plan-ending-emails.md`.
- **Sequences.** Written and edited in FluentCRM, not in the application. Each tag earns its place only if a real campaign sits behind it, so start with the tags that have one rather than building a sequence for every tag.
- **Segments.** Broadcasts are sent from FluentCRM to lists selected by these tags. The application builds no broadcasts and sends no announcement email. Members unsubscribe in FluentCRM itself.
- Priority support is a FluentSupport tag set through the CRM. It needs no work in the application.
- **Settings, Auto Sync User Data and Contact Data:** tick "Enable sync between WordPress user data and FluentCRM contact data", so a member's email change on Settings reaches their contact when the plugin changes their WordPress account (Data-Model 12e). It is off by default and nothing else moves the contact's email (owner, 29 October 2026). Leave the other options on that screen off: deleting a contact with its WordPress user, creating contacts on WordPress registration, role-based tags, comment form sign-up and the FluentCart checkout checkbox. Tags and deletes come from the application's CRM outbox. The plugin also keeps FluentCRM's sign-up, automation and role-based tagging listeners away from the WordPress users it makes for members, so these settings cannot add contacts or tags for them.
- **Registration closed.** In Settings > General, "Anyone can register" stays off on both sites (4 November 2026). Members receive their WordPress user from Botters Lab or a FluentCart purchase only. In All-In-One Security, "Manual registration approval" stays off, because a user it marks pending cannot sign in to the support desk.

## 4. FluentAffiliate

**When:** phase 3.

- **Programme settings.** Switch off FluentAffiliate's public sign-up form: members join only from within the application, which creates the affiliate record through the API, so every affiliate is linked to a member through `user.fluent_affiliate_ref`. Staff never add an affiliate in the WordPress admin.
- **The commission rates.** Set Commission Rate to 50% and Renewal Rate to 20% in the programme settings, so FluentAffiliate's own dashboard is roughly right (owner, 31 October 2026). Never set either to 0, since a referral worth nothing may be dropped and never reach the application. An upgrade shows at the Commission Rate there while the application pays its recurring rate. Staff alone see these figures. It is single level: there are no tiered or multi-level commissions.
- **No FluentAffiliate portal page.** Do not publish a page holding `[fluent_affiliate_portal]`: it would show affiliates FluentAffiliate's figures, which are not what is paid. Members follow their commissions on the Affiliates page in the Botters Lab.
- **Order bumps (FluentCart Pro, Promotions).** Create bumps from digital one-time products only, such as an ebook or a course. Never use a booster pack or a physical product as a bump: a pack on a plan order grants nothing and a physical product's shipping would count as plan. Turn conditions on naming the plan variations, because otherwise a bump shows on every cart. Leave "Enable Coupon Discount on top of offer discount" unticked on every bump. From FluentCart 2.3.1 a bump needs a discount above zero, so show a higher normal price discounted to the bump's price or give a token discount. The application reads each bump line after discount, so commission is unaffected. Commission is paid on the plan alone, whatever FluentAffiliate's own dashboard shows for the order. FluentCart offers no bump on an upgrade cart. Refund a bump in FluentCart against its own line on the order, for exactly that line's amount. Refund a plan in one go. Do not turn a bump on until one real mixed order has been checked on the test site.
- **The application works out and pays the real amount**, from its own rates and the paying member's own history, because FluentAffiliate cannot tell a new member from an upgrade. FluentAffiliate's figure is never paid. The rates are settings, recorded here so the WordPress side can be read against them: 50% of a member's first ever payment whatever the tier and 20% of every later payment, renewals and the first payment after an upgrade or a downgrade included. There is no Apprentice special case.
- **Leave Disable Self Referral off.** FluentAffiliate confirmed on 18 September 2026 that it has this setting, which blocks a commission where the buyer matches the affiliate's own account or payment details. It stays off deliberately. The application reads every referral through the API and works out every amount itself, so a referral FluentAffiliate suppresses is one the application never sees: it would never reach Commission review as a `self_referral` row and staff would have no record of it. The application's own checks are stricter in any case. It skips a referral where the affiliate is the payer or their email matches and refers one to staff on a matching card fingerprint. There is no IP address check, since the referral click happens on the WordPress site and the application never sees it.
- **Leave Disable Referrals on Upgrades off.** FluentAffiliate confirmed the same day that its FluentCart integration can stop an upgrade purchase creating a referral. It stays off for the same reason. An upgrade earns `affiliate.recurring_rate` under the application's own rules, so a suppressed upgrade referral would be a commission the application never learns about and never pays.
- Set the default referral format to Affiliate ID. FluentAffiliate cannot hold a custom affiliate code and FluentCart builds the WordPress username from the email address, so its links carry the affiliate id.
- **The referral link members see is the application's.** `/r/{username}` on the configured base URL looks the member's `user.fluent_affiliate_ref` up and redirects to the marketing site with FluentAffiliate's referral parameter and that id. An unknown username or a member outside the programme redirects with no parameter. Members therefore only ever see their own username and no domain is written into code.
- Turn referrals on subscription renewals on, so a renewal creates a referral as a first payment does. The application then applies its own recurring rate to it. Two switches must both be on: Affiliate Commission on Subscription Renewal on Referral Settings and Enable Referrals on Subscription Renewals on FluentCart's integration settings, which only shows once the first is saved.
- **Disable Referrals on Upgrades shows ticked even when nothing is saved.** Untick it before saving that screen because otherwise every upgrade stops earning.
- **Tick Lifetime Commissions on Referral Settings** with a Lifetime Rate above 0 and no expiry, so an upgrade by a referred member earns with no cookie, however long after the first purchase and on any device (owner's design that every later payment earns; checked in FluentAffiliate's code on 31 October 2026).
- Annual plans need no change. FluentAffiliate already records one referral per payment, so a yearly payment creates a referral like a monthly one.
- Leave Exclude Tax and Exclude Shipping on. FluentAffiliate calculates commission before tax, which is its default and matches the application's own splits.
- **Rejection.** FluentAffiliate rejects a referral on a full refund and reduces it on a partial one, but only until it is paid out. It has no approval delay, so nothing is configured for the wait: the application applies it when importing, by asking for a batch with an end date `sales.refund_period` days ago.
- **Leave Holding Period at 0** on Referral Settings. The application already waits `sales.refund_period` days through the end date it sends, so a holding period only adds delay.
- **Payout.** FluentAffiliate calculates commissions but never pays them. The daily batch creates a payout batch through the API, imports its transactions and its nightly Commission payment step pays them into the affiliate's earnings with no staff action, as does Pay commissions on the Commission review page (spec 8E.28d) when pressed, marking each affiliate's transaction paid in FluentAffiliate one at a time. So no payout is made through FluentAffiliate itself. Its payout method setting stays at its default, `paypal`, which makes `payment_email` a required field when an affiliate is created: the application sends the member's email as `payment_email` and `active` as the status when it creates the record.
- **API access** is the Application Password from section 1. It is also what the member area's Affiliates page reads referrals with.
- **The REST API question is closed.** FluentAffiliate answered on 17 September 2026 that `GET /wp-json/fluent-affiliate/v2/affiliates/{id}/referrals` lists an affiliate's referrals with their status, amount, currency, provider reference and their created and updated dates, with paging, search and status filtering. Date filtering is not a query parameter, so the application filters what comes back. No plugin is needed for referrals.
- **No payout on a day with nothing due.** FluentAffiliate 1.7.0 opens no payout when no referral is due, so its Payouts list gains nothing that day and the application saves nothing.
- **After each FluentAffiliate update, check the commission import.** The next morning, open Batch jobs in the Back Office and check that Affiliate commission import finished with no failure. Then read the daily report for a section starting Payout batch or a Commission import line about referrals that could not be imported. If either appears on two mornings running, report it before updating anything else.
- **Recovering a lost payout batch.** If the daily report names a payout id and end date the import could not read, FluentAffiliate holds that batch's referrals as paid while the application has no row for them. Do this only for a payout the daily report names, never for one the application has imported, since FluentAffiliate does not stop a paid transaction being deleted and its referrals would then be offered for payment twice. In FluentAffiliate's Payouts screen open that payout. It holds one transaction row for each affiliate in the batch: for each row open its menu, choose Delete and confirm, which marks that affiliate's referrals unpaid again (proved on the test site on 19 October 2026, `docs/reviews/fluent-affiliate-payout-recovery-19-october.md`). FluentAffiliate cannot delete or cancel the payout itself, so the emptied payout stays in the list with a total of 0 and blocks nothing. The next daily import takes the referrals in a new batch.
- **Never delete an affiliate's WordPress user first.** FluentAffiliate does not tidy up when a WordPress user is deleted, so its affiliate, referrals and payouts are left pointing at a user that no longer exists and its Payouts screen then fails on them. Delete the affiliate in FluentAffiliate first, which removes its referrals and visits, then the WordPress user. The application itself never deletes either: closing an account and a ban only deactivate the affiliate.

## 6. The secrets created here

Each is created by the human at the phase named and never written into a document or committed.

| Secret | Created in | Lives in | Needed by |
|---|---|---|---|
| Application Password for FluentCart's API | The WordPress user's profile | The application's `.env` | Phase 1 |
| Application Password for the FluentAffiliate and FluentCRM APIs | The WordPress user's profile | The application's `.env` | Phase 3 |
| FluentCart's Stripe API keys | Stripe | `wp-config.php` | Phase 1 |
| Signing secret of the Stripe endpoint to FluentCart | The Stripe CLI forward locally, the Dashboard endpoint live | FluentCart's Stripe settings | Phase 1 |
| The shared secret `btv_checkout_guard` sends, a random value of at least 32 characters | Chosen by the human | The plugin's settings screen and the application's `.env` as `CHECKOUT_GUARD_SECRET` | Phase 1 |
| The billing sign-in secret, at least 32 characters, which also signs members in to the support desk and the feedback page | Chosen by the human | The plugin's settings screen and the application's `.env` as `BILLING_HANDOFF_SECRET` | Phase 4 |
| The secret header value each of FluentCart's five feeds sends | Chosen by the human | FluentCart's feed settings and the application's `.env` | Phase 1 |

Every live counterpart is created again on the live account at phase 4 item 9 and entered there by hand. None of them ever touches the build.
